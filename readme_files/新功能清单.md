# robot_connect — 机器人调度系统

> 工业机器人调度中间件，将工厂 HTTP 命令转换为 ROS 机器人动作（导航 / 机械臂 / PLC）。

---

## 系统概览

`robot_connect` 是运行在机器人计算单元（或工控机）上的 Python 服务，通过 HTTP API 接收上位系统（MES / HMI / SCADA）发来的工序指令，将其转换为具体的机器人动作，并将执行结果回传。

```
上位系统（MES / HMI）
        │ HTTP JSON
        ▼
  ┌─────────────────────────────┐
  │       robot_connect         │
  │                             │
  │  HTTP Server (port 8090)    │  ← 接收命令
  │       │                     │
  │  programs/TJSH/             │  ← TJSH 调度项目（通用分液 / 转运）
  │  programs/ATC/              │  ← ATC 零件转移项目
  │  programs/AJL_anjielun/     │  ← AJL 色谱仪放样项目
  │  programs/WRC_FLOW/         │  ← WRC 图形化流程编排试点（JSON 流程图驱动）
  │       │                     │
  │  hardware/                  │  ← ROS 机器人控制层（导航 / Service）
  │  infrastructure/            │  ← 配置 / 日志 / 常量 / 持久化
  │  network/                   │  ← HTTP 客户端 / WebSocket 服务器 / 流程编辑器 API
  │  core/flow_engine.py        │  ← 通用流程执行引擎（图形化编排的核心）
  └─────────────┬───────────────┘
                │ ROSBridge WebSocket
                ▼
      机器人 ROS 系统（Navigation / 机械臂 Service / PLC）

  flow_editor/（独立静态前端，独立端口 8099）
        │ 拖拽式流程编辑 + 校验 + 演练(dry-run)
        ▼
  network/flow_api_server.py ──调用──► core/flow_engine.py（用 mock 机器人跑一遍）
```

### 关键目录

| 目录 | 职责 |
|---|---|
| `programs/TJSH/` | TJSH 项目：通用分液 / 转运调度（核心命令处理器 `CmdHandler`）|
| `programs/ATC/` | ATC 项目：两台机器人并行零件转移 + 传送带 PLC 控制 |
| `programs/AJL_anjielun/` | AJL 项目：单台机器人色谱仪自动放样 |
| `programs/WRC/` | WRC 项目：演示装配流程（硬编码实现，生产运行的版本） |
| `programs/WRC_FLOW/` | WRC 图形化流程编排试点：与 `WRC/` 完全独立，流程改成 JSON 驱动 |
| `hardware/` | ROS 控制封装：导航 Action、Service 调用、电量监控、位姿工具 |
| `handlers/` | 命令分发基类、异步任务完成回调（`callback_sender`） |
| `infrastructure/` | 配置加载（`config_loader`）、导航点位加载（`pose_loader`）、错误日志、常量、存储管理 |
| `network/` | HTTP 服务器（接收命令）、HTTP 客户端（调外部 API）、WebSocket 服务器 / 客户端、图形化流程编辑器 API `flow_api_server.py`（独立端口） |
| `core/` | 任务状态机（`ParallelTaskStateMachine`）、机器人动作、槽位计数器、通用流程编排引擎 `flow_engine.py`（见下方"图形化流程编排"） |
| `mock_rosbridge/` | 本地 ROSBridge 模拟器，用于离线测试与流程"演练"(dry-run) |
| `flow_editor/` | 零依赖拖拽流程编辑器（纯 HTML/CSS/JS，浏览器打开即用，不需要 Node.js） |
| `programs/WRC_FLOW/` | WRC 的"流程图编排版"试点，与 `programs/WRC/` 互不影响，可通过 `active_project` 切换 |

## 导航点位配置说明

各项目的导航点位统一存放在各自的 `robot_config.json` 中，加载优先级如下：

```
1. /config/robot_config.json          ← Docker 外部挂载（现场调试，最高优先级）
2. programs/<项目>/robot_config.json   ← 项目内置配置（代码仓库随项目一起发布）
3. infrastructure/robot_config.json   ← 基础兜底配置（含所有项目点位）
```

**防呆机制（`infrastructure/pose_loader.py`）：**

| 情形 | 处理方式 |
|---|---|
| config 中某 key 不在默认值里（拼写错误）| ⚠️ 警告打印 + 忽略该 key |
| 默认值里的 key 在 config 中缺失 | ⚠️ 警告打印 + 使用硬编码默认值 |
| config 中坐标格式非法 | ⚠️ 警告打印 + 使用硬编码默认值 |
| 所有 config 文件均不存在 | ⚠️ 警告打印 + 全部使用硬编码默认值，不崩溃 |

**修改点位坐标方法：** 在 `/config/robot_config.json`（Docker 挂载目录）或各项目 `robot_config.json` 的 `navigation_poses.<项目名>` 节下按格式修改，**重启后生效**。

## 🔄 最新更新 (2026-08-13) — 图形化编辑器修复：前后端 schema 对齐 + plc_action/find_slot 节点 + 流程还原度提升

在实机测试图形化编辑器时发现，上一版前端 `flow_editor/app.js`（渲染逻辑更完整：
分类节点面板、input/output 端口、键盘删除等）与后端 `core/flow_engine.py` /
`programs/WRC_FLOW/node_handlers.py` 提供的 schema **数据格式不一致**，
导致节点面板显示为空、节点无法拖动、加载已有流程时连线分支信息丢失等一系列
表现。逐一定位修复：

### 修复的问题

| 现象 | 根因 | 修复 |
|---|---|---|
| 节点面板没有节点、拖不动 | 后端 `*_NODE_TYPE_SCHEMAS` 的 `fields` 是字典 `{字段名: {...}}`，前端按数组 `field.name`/`field.forEach` 读取，触发 JS 异常导致渲染中断 | 统一改成有序数组格式：`fields: [{name, type, label, ...}, ...]`，并补充 `category` 分组字段 |
| 加载已有流程时，节点全部叠在同一个像素点，看起来"没有节点/拖不动" | 前端加载缺省坐标时把所有节点都摆在同一个 `(100,100)` | 改成按顺序网格布局（`60 + i%5*220, 60 + i/5*140`） |
| 加载/保存流程后分支信息（`true`/`false`/`success`/`failure`）丢失，流程图连线看起来不对 | 后端 JSON 规范的边字段是 `when`，前端内部用的是 `branch`，两者没有互相映射 | 加载时 `when → branch`，保存/校验/演练时 `branch → when`，双向映射 |
| 点"校验"永远显示失败 | 后端返回 `{success, errors}`，前端读取了不存在的 `res.valid` | 前端改读 `res.success` |
| 打开编辑器报 `GET .../node-types 404` | 前后端接口路径一个用下划线 `node_types`、一个用短横线 `node-types` | 统一成短横线 `node-types` |
| 节点端口位置错乱、缺少分类标题/分支配色等样式 | `flow_editor/style.css` 是配合旧版 `app.js` 写的，没有跟着更新 | 补齐 `.palette-category`、`.node-port.port-in/port-out`、`.branch-true/false`、`.node-label`、`.btn-delete` 等样式 |

### 新增能力

- **`FlowContext` 支持动态变量名模板**：`set_variable`/`condition` 节点的
  `var` 字段现在也会经过 `ctx.render()`，可以写
  `"var": "{{p3_n}}_state"` 这种"变量名本身也是模板"的写法，配合下面的
  `find_slot` 节点可以表达"操作刚找到的那个具体槽位"这类动态分支，不需要为
  每个具体槽位单独画一份 `condition`/`set_variable`。
- **新增 `plc_action` 节点类型**（`programs/WRC_FLOW/node_handlers.py`）：
  对接 `programs/WRC/plc_modbus.ConveyorController`（正转/反转/停止 +
  等待完成）；未配置传送带实例时优雅降级为跳过并返回成功，不阻塞流程图，
  为以后接 PLC/传送带类项目预留好节点类型。
- **新增 `find_slot` 节点类型**：按状态在一组槽位变量（如
  `P3_1_state`/`P3_2_state`）里查找第一个匹配的槽位并写入上下文变量，用来
  还原 `programs/WRC/WRC.py` 里 `SlotTracker.find_slot_by_state` 的
  "动态选一个可用槽位"分支逻辑，找不到时走 `failure` 出边。
- **`send_operation` 新增 `service` 字段**：`call_type=service` 时可选择
  走 `robot_task`（零件抓放/装配）还是 `robot_task_geely`（搬箱子），对照
  `WRC.py` 里两个 service 通道的区分。

### `wrc_flow_main.json` 示例流程大幅提升还原度

之前的示例流程只有 18 个节点，是简化版分拣/装配循环，与 `WRC.py` 实际的
动态选槽位、P4 三态分支（无箱直搬 / 空箱换箱 / 已满等待腾空）等逻辑有明显
差距。重写后达到 **76 个节点、104 条边**，完整对照
`_execute_trans_component_async`（robot_a）与 `_execute_assemble_async`
（robot_b）两条并行循环的真实控制流，包括：

- 用 `find_slot` 动态选择 P3 空箱/无箱槽位（而不是写死 `P3_1`）
- P1/P3/P4 状态用上下文变量表示（`p1_state`/`P3_1_state`/`P3_2_state`/
  `p4_state`），两条并行分支共享同一个 `FlowContext` 实现同步，等价于
  `WRC.py` 里两个线程共享同一组 `SlotTracker` 实例
- P4 三态分支完整还原：`FULL` 时轮询等待装配腾空、`NO_BOX` 时直接搬箱、
  `EMPTY` 时先换箱再搬箱
- 按 P1 剩余零件决定回 `home` 还是回 `P1` 继续下一轮分拣

已通过：JSON 结构校验（`validate_flow_graph`）、真实 mock 机器人端到端演练
（`network/flow_api_server.py` 的 `/dryrun` 接口）、以及用即时桩函数快速跑
多个周期验证所有分支（无箱直搬 / 换箱 / 回 home / 回 P1）都能正确触发。

详见 [`core/FLOW_ENGINE_GUIDE.md`](../core/FLOW_ENGINE_GUIDE.md)、
[`programs/WRC_FLOW/README.md`](../programs/WRC_FLOW/README.md)。

## 🔄 最新更新 (2026-08-12) — 图形化流程编排引擎（Flow Engine）+ WRC_FLOW 试点

### 背景

现有每个项目的业务流程都硬编码在 Python 函数里（导航 → 抓取 → 放置 → 等信号 → ...），
改流程 = 改代码 = 重新打包部署。为了让打包成 docker 后的现场操作人员也能自己调整业务
流程（拖拉接线、设置并行任务、简单组装/变更全流程任务），新增一套"流程图编排"能力。

### 新增模块

| 文件/目录 | 职责 |
|---|---|
| `core/flow_engine.py` | 通用流程图执行引擎：解释执行 JSON 描述的流程图（顺序/条件分支/并行/循环/延时/等待外部信号/暂停恢复/停止），机器人相关的"动作类"节点由各项目自己注册处理函数，引擎本身不 import 任何硬件层代码 |
| `core/FLOW_ENGINE_GUIDE.md` | Flow Engine 架构说明文档（流程 JSON 规范、内置节点类型、演练模式原理、如何新增试点项目） |
| `network/flow_api_server.py` | 图形化编辑器的后端 API 服务，**独立端口**（默认 8099，与命令端口 8090 完全分开），提供流程加载/保存/校验/演练接口，同时托管 `flow_editor/` 静态页面 |
| `flow_editor/` | 零依赖拖拽流程编辑器（纯 HTML/CSS/JS，浏览器打开即用，不需要 Node.js 构建环境，可直接随 docker 镜像打包部署） |
| `programs/WRC_FLOW/` | 首个试点项目：把 `programs/WRC/WRC.py` 的分拣/装配循环改写成流程 JSON，验证整套机制；与 `programs/WRC/` 完全独立、互不 import、互不影响，通过 `active_project` 配置切换 |

### 核心设计要点

- **合并"发操作动作"节点**：原来讨论的 `robot_task`（actionlib）与 `service_call`（ROS
  service）收敛成同一个节点类型 `send_operation`，通过 `params.call_type` 二选一
  （`action`/`service`），用户只需要切一个下拉框，不需要理解底层协议差异。
- **循环用环形连线表达**：不设专门的 loop 节点类型，某节点出边连回前面节点即可形成循环，
  与 Node-RED / n8n 等图形化工具的通用做法一致，画布上直观地表现为一个环。
- **暂停/恢复/停止复用现有语义**：`FlowEngine` 接收项目已有的 `pause_event` /
  `stop_event`（与 `WRC.py` 现在的 `_pause_event`/`_stop_event` 完全一致），
  `PROCESS_PAUSED`/`PROCESS_RESUMED`/`PROCESS_ENDED` 命令入口几乎不用改代码。
- **演练模式零额外开发**：机器人连接目标（真实 rosbridge / `mock_rosbridge_server.py`）
  本来就只是配置项，演练时只需要把 handler 注册表里的机器人实例换成连接 mock 的临时
  实例，`FlowEngine` 和节点处理器代码完全复用，不需要单独写一套模拟逻辑。`dryrun_adapter.py`
  会先探测 mock 端口是否可达，不可达就自动用子进程拉起
  `mock_rosbridge/mock_rosbridge_server.py`（最多等 6 秒），仍不可达则跳过该机器人的
  `connect()`，避免拖住整个 HTTP 请求。已通过端到端测试验证：演练完整跑通两条并行分支
  并返回逐节点执行轨迹，供前端在画布上高亮回放。
- **参数面板由 schema 驱动**：每种节点类型（内置 + 项目自定义）都提供一份字段 schema
  （`core/flow_engine.py` 的 `BUILTIN_NODE_TYPE_SCHEMAS` + 项目 `node_handlers.py` 的
  `NODE_TYPE_SCHEMAS`），前端据此自动生成参数编辑表单，新增节点类型不需要改前端代码。
- **前端技术选型**：评估过 React Flow 方案，最终选择零依赖原生 JS（浏览器直接运行，
  不需要 Node.js/npm），部署时只需拷贝静态文件，不给现场部署环境增加任何新的运行时依赖；
  后端 API 与前端实现完全解耦，以后如需更复杂交互可平滑替换前端而不影响后端。
- **流程文件存放位置**沿用现有配置分层习惯：`/config/flows/<flow_id>.json`（Docker 外部
  挂载，最高优先级）> `programs/<project>/flows/<flow_id>.json`（项目内置）；保存前自动
  备份旧版本（`<flow_id>.json.bak.<timestamp>`），方便回滚。

### 使用方式

```bash
# 1. 启动图形化编辑器后端（独立进程/端口，不影响现有命令服务）
python3 -m network.flow_api_server

# 2. 浏览器打开
http://<主机IP>:8099/

# 3. 编辑 WRC_FLOW 试点流程、保存、点"▶ 演练"验证效果（自动连 mock，不影响生产机器人）

# 4. 切换到 WRC_FLOW 运行（active_project 改为 "WRC_FLOW"），对外命令接口与 WRC 一致：
#    PROCESS_BEGINS / PROCESS_PAUSED / PROCESS_RESUMED / PROCESS_ENDED / MANUAL_RESET_COMPLETED
```

详见 [`core/FLOW_ENGINE_GUIDE.md`](../core/FLOW_ENGINE_GUIDE.md)、
[`programs/WRC_FLOW/README.md`](../programs/WRC_FLOW/README.md)、
[`flow_editor/README.md`](../flow_editor/README.md)。

## 🔄 最新更新 (2026-07-21) — 异步任务完成回调 `CallbackSender`

任务（如 KAIAO 的 `PICK_BOX_TO_SP` / `PICK_COMPONENT_TO_SP`）在后台跑完后，
系统可主动 **HTTP POST** 结果到上位系统（WCS / MES）。实现位于
`handlers/callback_sender.py`，传输复用 `network/http_client.py`。

### 配置（`robot_config.json` → `callback`）

```json
"callback": {
  "enabled": true,
  "url": "http://192.168.161.202:50005/wcs/humanoidRobot/updateTaskState",
  "timeout": 10,
  "retry": 3,
  "retry_interval": 10
}
```

| 字段 | 说明 | 默认 |
|---|---|---|
| `enabled` | 是否启用回调 | `false` |
| `url` | **完整**回调地址（含 scheme / host / port / path） | `""` |
| `timeout` | 单次请求等待对方响应的超时（秒） | `10` |
| `retry` | 失败后额外重试次数（总尝试 = retry + 1） | `0` |
| `retry_interval` | 两次尝试间隔（秒） | `10` |

配置由 `infrastructure.config_loader.get_callback_config()` 读取；
`reload_config()` / `RESET_SYSTEM` 会调用 `reset_callback_sender()` 刷新单例。

**KAIAO 当前默认**：`programs/KAIAO/robot_config.json`（及基础设施副本）里已启用上述 WCS 地址。

### URL 形式说明（支持带路径的完整地址）

`CallbackSender` 用 `urllib.parse.urlparse` 拆分 `url`：

| 完整 URL | 拆分结果 |
|---|---|
| `http://192.168.161.202:50005/wcs/humanoidRobot/updateTaskState` | base=`http://192.168.161.202:50005`，path=`/wcs/humanoidRobot/updateTaskState` |
| `http://127.0.0.1:8099/callback` | base=`http://127.0.0.1:8099`，path=`/callback` |

随后执行 `HttpClient.post(path, json_body=...)`，最终请求 URL 为
`base + path`，**多级路径、非默认端口均可**，与 WCS 这类地址兼容，无需改代码。

注意：
- `url` 必须带 `http://` 或 `https://`
- path 建议以 `/` 开头（标准 URL 解析会自动带上）
- 查询串（`?a=1`）当前未单独透传；若需要 query，请写进完整 `url` 并确认 `urlparse` 后 path 仍正确（一般业务把参数放 JSON body 即可）

### 回调请求体（POST JSON）

```json
{
  "cmd_id":   "PICK_BOX_TO_SP_001",
  "cmd_type": "PICK_BOX_TO_SP",
  "success":  true,
  "message":  "搬运完成: ...",
  "data":     {}
}
```

`data` 仅在业务传入时出现。发送在**后台线程**中进行，不阻塞任务主流程。

### 对方必须如何确认

成功判定**不是**默认的 `statusCode == 0`，而是自定义 checker：

```json
{ "received": true }
```

- HTTP 须为 2xx，且响应 JSON 中 **`received` 严格等于布尔 `true`**
- 否则视为未确认，按 `retry` / `retry_interval` 重发
- 若 WCS 实际返回其它字段（如 `code: 0` / `success: true`），需对方改协议，或改
  `CallbackSender._callback_success_checker` 适配

## 🔄 最新更新 (2026-06-12) — ATC 导航后流程卡死修复 + `is_robot_at_pose` 增强

### 1. 修复 ATC 项目导航完成后流程卡死问题

**问题根因：** `MANUAL_RESET_COMPLETED` 触发传送带正转后，若 PLC 不可连接（测试环境无 PLC / pymodbus 未安装），传送带指令立即失败，但代码只在 `conveyor_done=True` 时才将 P1 设为 FULL。`robot_a` 线程导航完成后在"等待 P1 物料就绪"循环中阻塞最长 30 分钟（`P1_WAIT=1800s`），表现为"导航运行完但后续操作不执行"。

**修复方案（`programs/ATC/ATC.py`）：**

```python
# _on_manual_reset() 后台线程（handle_manual_reset_completed 内）
conveyor_done = self._run_conveyor_forward()

# 旧逻辑：仅在 conveyor_done=True 时才设 FULL → 无 PLC 时卡死
# 新逻辑：无论传送带是否成功都设 FULL；PLC 失败时打印 WARNING 但不阻塞主流程
if conveyor_done:
    logger.info("ATC", "传送带正转成功，P1 已设置为 FULL")
else:
    logger.warning("ATC", "传送带正转失败（PLC 不可用或未安装 pymodbus），降级模式：直接将 P1 设为 FULL")
self._p1_tracker.set_state("P1", BoxSlotState.FULL)
```

这与 `ConveyorController` 文档中声明的设计意图一致：*"若 pymodbus 未安装或 PLC 连接失败，则降级为仅记录日志，不影响主流程。"*

### 2. `is_robot_at_pose` 支持多段路径（list-of-tuples）

**背景：** 所有 `NavigationPose` 属性（如 `NavigationPose.P1`、`NavigationPose.P1_mid`）在 `load_nav_poses` 加载后均为 `list-of-tuples` 格式（例如 `[(-0.96, -0.92, ...)]`），而旧版 `is_robot_at_pose` 只接受单个 7 元素元组，导致调用时触发 `TypeError`（被 `except` 吞掉后返回 `False`），既无法正确判断位置，又在每次调用时等待 5 秒 odom 超时。

```python
def is_robot_at_pose(robot, target_pose, ...):

    if isinstance(target_pose, (list, tuple)) and isinstance(target_pose[0], (list, tuple)):
        target_pose = target_pose[-1]
    ...
```

**适用场景：**

| `is_robot_at_pose(robot, (x,y,z,qx,qy,qz,qw))` | 单元组，直接使用 |

**涉及文件：**
- `hardware/navigation_utils.py` — `is_robot_at_pose` 签名及文档更新

## 🔄 最新更新 (2026-04-22) — Action 客户端三层抽象

本轮重构：**把"ROS Action 传输机制"与"具体 Action 的业务语义"解耦成三层**，
新增 `hardware/task_utils.py`，让导航与操作共用同一套通用 Action 客户端。
对外完全向后兼容。

### 🎯 目标与动机

之前 `hardware/action_utils.py` 同时承担了两件事：

1. **通用传输**：actionlib topic 协议（发 Goal、订 Feedback/Result、发 Cancel、重连）
2. **业务语义**：`send_chem_project_action`、`_chem_project_success_check`、
   `CHEM_PROJECT_ACTION_SPEC`、`NAVIGATION_ACTION_SPEC`

这两件事混在同一个文件里会导致：

- 新增一个 Action 类型（比如以后的臂控 Action）必须碰同一个"通用层"文件
- `action_utils` 理论上应该"永远不知道"业务是什么，但是它在 import `ROSTopic` 的业务常量
- 业务代码想用 feedback 时要写 `fb.inner.get('status')` / `fb.inner.get('current_params')`——领域语义被泄漏成原始 dict

本轮把它们拆成**三层**：

| 层次 | 文件 | 职责 | 是否知道"这是什么 Action" |
|---|---|---|---|
| 传输层 | `hardware/action_utils.py` | Goal/Feedback/Result/Cancel 的 topic 级收发、goal_id 管理、超时、断线重连 | **否**，完全通用 |
| 领域层（导航） | `hardware/navigation_utils.py` | `NavigationGoal` / `NavigationResult` / `send_navigation_action` | 是，只懂导航 |
| 领域层（操作） | `hardware/task_utils.py` **[新]** | `TaskFeedback` / `TaskResult` / `send_task_action` | 是，只懂"任务/操作"契约 |

> **规则**：
> - 已有领域封装 → 用 `navigation_utils` / `task_utils`，拿到的是**领域数据结构**。
> - 新增一个**完全新契约**的 Action → 直接 `action_utils.send_action()` + 自定义 `succeeded_check`。
> - **不要**再往 `action_utils` 里加业务 Spec。

### 📦 文件变更总览

| 文件 | 变更 |
|---|---|
| `hardware/action_utils.py` | **精简**：移除 `NAVIGATION_ACTION_SPEC`、`CHEM_PROJECT_ACTION_SPEC`、`send_chem_project_action`、`_chem_project_success_check`；不再 import `ROSTopic`/`ROSTopicMessageType` |

### 📡 actionlib 五路 Topic 与消息类型

所有 Action（任务 `/robot_task/*`、化学项目 `/chem_project/*`、导航 `/zj_humanoid/navigation/navigation/*` 等）
在 rosbridge 上均走 **actionlib 的 5 个 topic**，**不是 Service**。

| 方向 | Topic | 消息类型 | 说明 |
|---|---|---|---|
| 发布 | `<base>/goal` | `<pkg>/<Name>ActionGoal` | 业务 Action 包，外层含 `header`、`goal_id`、`goal` |
| 订阅 | `<base>/feedback` | `<pkg>/<Name>ActionFeedback` | 业务 Action 包，外层含 `header`、`status`、`feedback` |
| 订阅 | `<base>/result` | `<pkg>/<Name>ActionResult` | 业务 Action 包，外层含 `header`、`status`、`result` |
| 发布 | `<base>/cancel` | **`actionlib_msgs/GoalID`** | actionlib 标准，**不是**业务 Action 类型 |
| 订阅 | `<base>/status` | **`actionlib_msgs/GoalStatusArray`** | actionlib 标准，**不是**业务 Action 类型 |

**Cancel**（`actionlib_msgs/GoalID`）——直接发布到 `cancel` topic，无外层包装：

```json
{
  "stamp": { "secs": 1696000005, "nsecs": 0 },
  "id": "robot_connect-1696000000123-a1b2c3d4"
}
```

- `id` 为空字符串 `""` → 取消该 Action 上**全部** Goal
- `id` 有值 → 只取消对应 `goal_id`

**Status**（`actionlib_msgs/GoalStatusArray`）——订阅 `status` topic 收到的数组：

```json
{
  "header": { "stamp": { "secs": 1696000000, "nsecs": 0 }, "frame_id": "" },
  "status_list": [
    {
      "goal_id": { "stamp": { "secs": 1696000000, "nsecs": 123456 }, "id": "robot_connect-..." },
      "status": 1,
      "text": "ACTIVE"
    }
  ]
}
```

`status_list[].status` 为 actionlib `GoalStatus` 枚举（uint8）：`0=PENDING, 1=ACTIVE, 2=PREEMPTED, 3=SUCCEEDED, 4=ABORTED, ...`

> **注意区分两层 `status`**：
> - **status topic** 上的 `GoalStatusArray` → actionlib 传输层状态
> - **feedback 外层**的 `status` 字段 → 同样是 `actionlib_msgs/GoalStatus`（带 `goal_id`）
> - **feedback 内层** `feedback.status` → 业务字符串（`.action` Feedback 段定义的 `string status`）

`cancel_task_action(robot, goal_id="")` 即向 `<base>/cancel` 发布上述 `GoalID`；
`send_task_action` / `send_action` 内部会订阅 `<base>/status` 辅助跟踪 Goal 生命周期。

### 🏷️ `.action` 文件内容与话题消息类型名的关系

真机侧常见定义文件为 `RobotAction.action`，三段内容与上表契约一致：

```
# Goal
navi_types/RobotTaskTypes robot_task_types
string task
string area
string extra_params
---
# Result
bool success
string error_msg
string return_params
---
# Feedback
string status
string current_params
```

**为何代码里写的是 `chem_project_msgs/ChemProjectActionGoal`，而不是 `RobotAction`？**

ROS / actionlib 的**话题消息类型名**由下面两项决定，**与 `.action` 里 Goal/Result/Feedback 的字段无关**：

| 决定因素 | 示例 | 作用 |
|---|---|---|
| **ROS 包名**（`package.xml` 里的 name） | `chem_project_msgs` | 类型前缀 |
| **`.action` 文件名**（去掉扩展名） | `ChemProject.action` → 动作名 `ChemProject` | 类型后缀 |

生成规则（`ActionSpec.from_action_info` 与此一致）：

```
goal_msg_type     = {pkg}/{Name}ActionGoal
feedback_msg_type = {pkg}/{Name}ActionFeedback
result_msg_type   = {pkg}/{Name}ActionResult
```

因此：

- `.action` 三段只定义 **内层** `goal` / `result` / `feedback` 的字段结构；
- rosbridge 传输时还会自动包一层 **actionlib 外壳**（`header`、`goal_id`、`status` 等），对应 `*ActionGoal` / `*ActionFeedback` / `*ActionResult` 类型；
- `cancel` / `status` 两个 topic 永远用 **`actionlib_msgs`**，不会随业务 `.action` 改名。

本仓库历史联调/mock 侧注册的是 **`chem_project_msgs` 包 + `ChemProject.action`**，故默认类型为：

- `chem_project_msgs/ChemProjectActionGoal`
- `chem_project_msgs/ChemProjectActionFeedback`
- `chem_project_msgs/ChemProjectActionResult`

KAIAO 仅把 topic 前缀改为 `/robot_task/*`，**字段契约相同**，故 `programs/KAIAO/constants.py` 仍沿用上述消息类型名。

若真机 `rosmsg show` / `rostopic info` 显示的实际类型不同（例如包名为 `robot_msgs`、文件为 `RobotAction.action` →
`robot_msgs/RobotActionActionGoal`），只需在对应项目的 `ActionSpec` 中改 `goal_msg_type` 等三个业务类型；
**cancel/status 仍为 `actionlib_msgs/GoalID` 与 `actionlib_msgs/GoalStatusArray`，不用改。**

同契约但前缀不同的 Action（比如 `/zj_humanoid/chem_project/*`）只需换 `ActionSpec`：

```python
from hardware.action_utils import ActionSpec
from hardware.task_utils import send_task_action

MY_SPEC = ActionSpec.from_action_info(
    action_base="/zj_humanoid/chem_project",
    action_pkg="chem_project_msgs",
    action_name="ChemProject",
)
res = send_task_action(robot, task="SCAN_TABLE", spec=MY_SPEC)
```

### 🔌 send_service_request 响应协议升级

#### 新协议响应结构

```json
{
    "op": "service_response",
    "service": "/chem_project_service",
    "values": {
        "success": true,
        "error_msg": "",
        "return_params": ""
    },
    "result": true
}
```

| 字段 | 类型 | 含义 |
|---|---|---|
| `result` | bool | rosbridge 层调用是否成功（service 存在、参数合法） |
| `values.success` | bool | 业务操作是否成功完成 |
| `values.error_msg` | str | 失败时的错误描述；成功为 `""` |
| `values.return_params` | str | 返回参数（通常为 JSON 字符串，如 CV 检测的 `pose`/`type`） |

**判定规则**：`operation_success = result AND values.success`

#### 旧协议字段已废弃

以下字段已从 `_async_send_and_receive` 中移除：
- `values.finish` — 不再使用
- `values.target_pose_return` / `values.type_return` — 并入 `return_params`
- `values.remaining` — 不再打印

#### RobotController 新增属性

每次 `send_service_request` 完成后，下列三个属性都会被刷新（失败/异常/通信错误也会清零而非脏读）：

| 属性 | 对应协议字段 | 说明 |
|---|---|---|
| `robot.last_service_success` | `values.success` | bool |
| `robot.last_service_error_msg` | `values.error_msg` | str |
| `robot.last_service_return_params` | `values.return_params` | str，通常是 JSON |

**用法**：`send_service_request` 返回值依然是 `True/False`，方便 `if not result:` 使用；如果需要 `return_params`，调用方在收到返回值后立刻读 `robot.last_service_return_params`。

#### CV 检测迁移示例

原先（三元组解包）：

```python
cv_detect_result, object_pose, object_type = robot.send_service_request(
    robot.get_robot_service(), "cv_detect", extra_params={"waist": "not_turing"}
)
```

现在（`return_params` 解析）：

```python
cv_detect_result = robot.send_service_request(
    robot.get_robot_service(), "cv_detect", extra_params={"waist": "not_turing"}
)
object_pose, object_type = _parse_cv_detect_return_params(robot.last_service_return_params)
```

**`_parse_cv_detect_return_params(return_params)`** 位于 `cmd_handler.py` 顶部，容错性：
- `None` / `""` / 非 JSON → 返回 `(None, None)` 并写 warning 日志
- 直接传 `dict` 也能处理（无需先序列化）
- 兼容两套键名：`target_pose_return` / `type_return` 和 `object_pose` / `object_type`

受影响的调用点：`cmd_handler.py` 里 2 处 CV 检测（`_execute_scan_qrcode_async` 系列）。

#### 失败日志样例

| 情况 | 日志 |
|---|---|
| 业务失败 + error_msg | `✗ Robot B 操作未完成: 未识别到瓶子` |
| result=false（service 不存在） | `✗ Robot A 服务调用失败: Service /xxx does not exist` |

### 🚦 导航地图下发：改"后台异步"为"阻塞等待再激活"

#### 问题

原先 `_schedule_auto_set_navigation_map()` 在后台线程跑，`connect()` 立即返回。系统会直接走到 `✅ 系统已激活，开始正常工作` 并允许接收 `SCAN_QRCODE` / `SPLIT_LIQUID` 等任务命令。若此时地图尚未下发完，任务一触发导航就会失败。

#### 方案

1. `RobotController.__init__` 新增事件 `self._nav_map_ready_event`（`threading.Event`）
2. `_schedule_auto_set_navigation_map()` 一进入先 `event.clear()`，worker 线程 `finally: event.set()`
3. 关闭开关 / 未配置 `navigation_map` → 立刻 `event.set()`，调用方不会空等
4. 新增公开方法 `RobotController.wait_for_navigation_map_ready(timeout=120.0)` → 阻塞等待
5. `main.py` 在 `init_cmd_handler(robots)` 之后、`battery_monitor.start()` 之前、`✅ 系统已激活` 之前，遍历所有**已连接**机器人 `wait_for_navigation_map_ready`

#### 新增属性（用于诊断）

| 属性 | 含义 |
|---|---|
| `robot._nav_map_ready_success` | 最近一次下发是否成功 |
| `robot._nav_map_ready_message` | 最近一次下发的消息（成功/失败原因） |

#### 启动日志时序

```
✅ robot_b 连接成功
重新初始化命令处理器...
⏳ 等待导航地图下发完成...
🗺 Robot B 已下发导航地图: test1          ← 后台线程打印
✓ robot_b 导航地图就绪 (已是目标地图)      ← main 线程打印
...
✅ 系统已激活，开始正常工作
```

#### 行为矩阵

| 情况 | 等待表现 | 是否激活 |
|---|---|---|
| 地图下发成功 | 返回 `True` | ✓ |
| 当前地图相同（`skip_if_same=true`） | `set_navigation_map` 快速返回 | ✓ |
| `auto_set_on_connect=false` 或未配 `navigation_map` | event 立刻 set | ✓ |
| 下发失败/超时 | 打警告继续 | ✓（带警告） |
| 机器人连接失败 | 不在 `connected_robots`，不等待 | ✓ |

**重连路径不变**：`_unified_message_listener` 触发的重连仍然是后台异步下发，不阻塞监听器。

### 🗺 连接机器人后自动下发导航地图

每次成功连接（含断线重连）后，系统会自动检测导航是否空闲并下发配置的导航地图，无需人工触发。

#### 工作流程

```
connect() / _async_reconnect() 成功
        │
        ▼ （后台线程，不阻塞 connect 返回）
_schedule_auto_set_navigation_map()
        │
        ▼
set_navigation_map(robot, "test1")
        │
        ├─► get_current_navigation_map()  调 get_cur_map_info
        │        │
        │       当前地图 == "test1" → 直接返回 (True, "已是目标地图")
        │       不同 → ↓
        │
        ├─► is_robot_navigating()   订阅 NAVIGATION_ACTION_STATUS，检查 status_list
        │     │                     只要存在 status ∈ {0,1,6,7} 即视为运行中
        │     │
        │    YES → wait_for_navigation_idle()  等最多 60s
        │    NO  → ↓
        │
        ▼
robot.call_service(ROSService.NAVIGATION_MAP_CONFIG, {"map_name": "test1"})
        │
        ▼
解析响应 {"map_name":..., "code":..., "message":...} → (success, message)
```

**关键判定逻辑（避免误判残留状态）**：机器人导航结束后，上一个终态（如 `status=3 SUCCEEDED`）会在 `status_list` 中残留一段时间。函数只看"是否存在 active 状态"，而不是"是否全部为终态"，因此不会把残留当作运行中。

#### 配置方式

在 `infrastructure/robot_config.json` 的每个机器人下加 `navigation_map` 字段：

```json
{
    "robots": {
        "robot_a": {
            "host": "172.16.8.128",
            "port": "9090",
            "robot_type": "robot_a",
            "enabled": true,
            "navigation_map": "test1"
        }
    }
}
```

**外部配置开关**（推荐，支持热改）—— 在 `infrastructure/robot_config.json` 顶层加 `navigation_map` 段：

```json
{
    "navigation_map": {
        "auto_set_on_connect": true,
        "wait_idle_timeout": 60,
        "service_timeout": 30,
        "skip_if_same": true
    }
}
```

| 字段 | 默认值 | 说明 |
|---|---|---|
| `auto_set_on_connect` | `true` | 总开关。`false` 时连接/重连后不自动下发地图 |
| `wait_idle_timeout` | `60` | 等导航空闲最长秒数 |
| `service_timeout` | `30` | set_map 服务调用超时秒数 |
| `skip_if_same` | `true` | 先调 get_cur_map_info，若已是目标地图则跳过下发 |

外部配置优先级高于 `infrastructure/constants.py` 的默认值。读取方式：

### 🛡 `send_service_request` 异常分流（修复误重连）

**原问题**：rosbridge 遇到服务不存在时回 `"values": "Service ... does not exist"`（字符串而非字典）。原代码对字符串调用 `.get()` 抛 `AttributeError`，被 catch-all 异常处理错误地标记为"连接断开"，触发级联的重连 + 重订阅。

**修复**：`hardware/robot_controller.py` 中做两处改进：

1. **业务错误提前返回**：解析 `values` 前先判断是否 dict，不是就打印错误信息、返回 `False`，不改 connected 状态。
2. **异常分流**：
   - `ConnectionError` / `OSError` / `asyncio.TimeoutError` → 标记断开并重连
   - 其他 `Exception`（解析 / 业务异常）→ 仅返回失败，不动 connected 状态

之后调用不存在的服务只会打印：
```
✗ Robot A 服务调用失败: Service /chem_project_service does not exist
```
不会再触发错误的重连 + 重订阅。

#### 功能说明

**Navigation.action 定义：**

```yaml
# Goal
std_msgs/Header header
TaskType task_type              # 任务类型 (0=Routine, 1=Charge, 2=Emergency)

std_msgs/Header header
duration duration              # 用时
float64 distance_deviation     # 到达距离偏差（m）
float64 heading_deviation      # 到达航向偏差（rad）
NavigationState state          # 完成状态（Succeeded/Failed/Cancelled/Aborted）
ErrorInfo[] causes             # 未成功原因

---

std_msgs/Header header
NavigationState state          # 算法状态
```

### 7. HTTP 状态码与业务错误码

本系统采用 **HTTP 状态码 + 业务错误码** 双层错误体系：
- **HTTP 状态码**：遵循 HTTP 标准，表示请求的传输层状态
- **业务错误码 (code)**：响应体中的 `code` 字段，表示具体的业务错误类型

#### HTTP 状态码说明

| HTTP状态码 | 说明 | 对应业务场景 |
|------------|------|-------------|
| **200** | 请求成功 | 操作成功完成 |
| **400** | 请求错误 | JSON格式错误、缺少参数、参数无效、未知命令类型 |
| **404** | 资源未找到 | 机器人不存在、任务不存在、资源未找到 |
| **408** | 请求超时 | 任务执行超时 |
| **409** | 资源冲突 | 机器人正忙 |
| **410** | 资源已删除 | 任务已取消 |
| **422** | 无法处理 | 资源不足、存储区已满 |
| **500** | 服务器错误 | 命令执行异常、系统重置失败、内部错误 |
| **502** | 网关错误 | 机器人服务调用失败 |
| **503** | 服务不可用 | 机器人未连接、功能未启用、命令处理器未初始化 |

### 11. 常见错误处理

| HTTP状态码 | 错误码 | 场景 | 解决方案 |
|-----------|--------|------|---------|
| 400 | 1001 | JSON格式错误 | 检查JSON语法，确保格式正确 |
| 400 | 1002 | 缺少必要参数 | 检查请求参数是否完整 |
| 400 | 1004 | 未知命令类型 | 检查 cmd_type 是否正确 |
| 404 | 2001 | 机器人不存在 | 检查 robot_id 是否正确，查看 available_robots 列表 |
| 503 | 2002 | 机器人未连接 | 检查机器人网络连接和 ROS Bridge 状态 |
| 409 | 2003 | 机器人正忙 | 等待当前任务完成或查询任务状态 |
| 404 | 3001 | 任务不存在 | 确认任务ID正确，任务可能已过期 |
| 503 | 4001 | 命令处理器未初始化 | 发送 START_WORKING 命令激活系统 |
| 503 | 2007 | 电量信息未获取 | 等待系统获取机器人电量信息 |
| 503 | 2008 | 机器人低电量 | 等待机器人充电完成 |
| 422 | 5001 | 资源不足 | 检查相关资源是否充足 |

### 12. 注意事项

1. **异步任务**：`SCAN_QRCODE`、`SPLIT_LIQUID`、`REFILL_EMPTY_BOTTLES`、`TRANSFER_TO_CHROMATOGRAPH` 为异步任务，发送命令后立即返回，需要通过 `GET_TASK_STATE` 查询执行状态。

2. **任务互斥**：同一机器人同时只能执行一个异步任务，发送新任务时如果机器人正忙会返回 HTTP 409。

3. **超时处理**：长时间任务建议设置合理的 `timeout` 参数。

4. **编码格式**：所有请求和响应均使用 UTF-8 编码。

5. **端口配置**：默认端口为 8090，可在 `constants.py` 或外部配置文件中修改。

6. **错误码体系**：系统同时使用 HTTP 状态码和业务错误码，HTTP 状态码遵循标准语义，业务错误码提供更细粒度的错误信息。

### 🔋 启动时电量检测功能

新增系统启动时等待电量信息的功能，确保机器人在接收任务前电量状态已知。

#### 功能说明

1. **启动等待**：系统启动后，会持续监听机器人电量信息，直到所有机器人的电量信息都已获取
2. **任务拒绝**：在获取到电量信息之前，系统会拒绝任务请求，返回 HTTP 503 和错误码 2007
3. **低电量检测**：获取到电量信息后，如果电量低于阈值，系统会先去充电再接收任务
4. **任务中不充电**：在任务执行过程中，即使电量降到阈值以下，也会等待当前任务完成后再去充电

#### 配置参数

在 `constants.py` 或 `robot_config.json` 中配置：

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `REQUIRE_BATTERY_INFO_ON_STARTUP` | bool | `true` | 是否在启动时等待电量信息 |
| `BATTERY_INFO_WAIT_TIMEOUT` | int | `60` | 等待电量信息的超时时间（秒），0表示无限等待 |

#### 配置文件示例

```json

        "enabled": true,

        "battery_wait_timeout": 60,

        "charging_done_threshold": 0.99,
        "charging_done_home_poses": {
            "robot_a": "home_transfer",

        }
    }
}
```

#### 工作流程

```
系统启动
    ↓
订阅电池状态topic
    ↓
┌─────────────────────────────────┐
│  等待电量信息（最长60秒）        │

│  错误码: 2007                   │
└──────────────┬──────────────────┘

    ↓                     ↓
电量正常              电量低于阈值
```

### 🔒 点位互斥锁 - 多机器人冲突避免

新增点位互斥锁模块，防止两台机器人在相邻点位同时操作时发生干扰。

#### 问题背景

当一台机器人导航到转运点位执行操作时，另一台机器人如果在对应的分液任务点位，两者的操作会相互干扰。

#### 冲突点位对

| 转运任务点位 | 分液任务点位 | 说明 |
|-------------|-------------|------|
| `WAITING_SPLIT_AREA_TRANSFER` | `WAITING_SPLIT_AREA_SPLIT` | 待分液区 |
| `SPLIT_DONE_250ML_AREA_TRANSFER` | `SPLIT_DONE_250ML_AREA_SPLIT` | 250ml分液完成暂存区 |
| `SPLIT_DONE_500ML_AREA_TRANSFER` | `SPLIT_DONE_500ML_AREA_SPLIT` | 500ml分液完成暂存区 |

#### 解决方案

当机器人A进入转运点位时：
1. 检查对应的分液点位是否被机器人B占用
2. 如果被占用，机器人A等待直到机器人B离开
3. 机器人A完成操作后释放点位锁，通知等待的机器人

反之亦然，当机器人进入分液点位时也会检查转运点位。

#### 使用方法

```python
from pose_lock import get_pose_lock
from constants import NavigationPose

pose_lock = get_pose_lock()

# 方式1: 上下文管理器（推荐）
with pose_lock.acquire_pose(robot_id, NavigationPose.WAITING_SPLIT_AREA_TRANSFER):
    # 导航到点位
    # 执行操作
    pass  # 离开时自动释放锁

# 方式2: 手动获取和释放
pose_lock.acquire(robot_id, NavigationPose.SPLIT_DONE_250ML_AREA_SPLIT)
try:
    # 执行操作
    pass
finally:
    pose_lock.release(robot_id, NavigationPose.SPLIT_DONE_250ML_AREA_SPLIT)
```

#### 状态查询

```python
# 检查点位是否被占用
is_busy = pose_lock.is_occupied(NavigationPose.WAITING_SPLIT_AREA_TRANSFER)

# 获取占用机器人ID
robot = pose_lock.get_occupying_robot(NavigationPose.WAITING_SPLIT_AREA_TRANSFER)

# 获取完整状态
status = pose_lock.get_status()
# 返回: {"occupied_poses": {"waiting_split_area_transfer": "robot_a"}, "waiting_robots": {...}}
```

| 文件 | 说明 |
|------|------|
| `pose_lock.py` | 点位互斥锁模块 |
| `constants.py` | `NavigationPose` 导航点位常量 |

## 🔄 更新 (2026-04-02)

### 🐛 修复 WebSocket 客户端固定 5 秒延迟问题

#### 问题描述

使用 `websocket_client.py` 与外部服务器通信时，外部服务器向机器人推送查询命令（如 `GET_UPPER_LIMB_JOINT_STATES`），机器人处理后发送响应，**始终延迟 5 秒**；而通过 HTTP 调用同一命令无此延迟。

#### 根本原因

`_handle_message` 是一个 `async` 协程，它在 WebSocket 客户端的 asyncio 事件循环中运行。原代码对 `_message_callback` 的调用是**同步**的：

```python
# 修复前（错误写法）
self._message_callback(data)
```

`_message_callback`（即 `main.py` 中的 `handle_server_message`）内部执行流程如下：

```
handle_server_message(data)
  ├─ get_cmd_handler().handle_command(data)   # 处理命令（含 ROS topic 轮询，可快速返回）
  └─ websocket_client.send(result)            # 向服务端发送响应
        └─ asyncio.run_coroutine_threadsafe(_send_async, self._loop).result(timeout=5)
                                              ↑ 向"当前正在被自己阻塞"的事件循环提交协程
                                              → 协程永远无法被调度
                                              → 精确等待 5 秒超时
```

这是经典的 **asyncio 自身死锁**：同步回调在事件循环线程内执行，再试图通过 `run_coroutine_threadsafe` 向同一个被阻塞的事件循环提交任务，导致 `future.result(timeout=5)` 超时。

#### 修复方案

在 `websocket_client.py` 的 `_handle_message` 中，将 `_message_callback` 的调用改为通过 `run_in_executor` 放入线程池执行，使事件循环保持空闲，`send()` 提交的 `_send_async` 协程可正常调度：

```python
# 修复后（正确写法）
loop = asyncio.get_event_loop()
await loop.run_in_executor(None, self._message_callback, data)
```

#### 修改文件

| 文件 | 位置 | 改动 |
|------|------|------|
| `websocket_client.py` | `_handle_message()` | `_message_callback(data)` 改为 `await loop.run_in_executor(None, self._message_callback, data)` |

> **注意**：此问题与 `websocket_server.py` 中 `_process_message` 的 `command_callback` 阻塞问题属同一类型，修复方式相同。HTTP 服务器无此问题，因为每个请求在独立线程中运行，不涉及 asyncio 事件循环。

#### 单例模式设计

`station_counter.py` 使用**单例模式 (Singleton Pattern)**，确保整个程序中只有一个计数器实例存在。

**实现方式：**
```python
_station_counter = None  # 全局变量，初始为空

def get_station_counter() -> StationCounter:
    global _station_counter
    if _station_counter is None:      # 第一次调用时创建
        _station_counter = StationCounter()
    return _station_counter           # 之后每次返回同一个实例
```

**为什么需要单例：**
- 程序中多个地方（如 `_scan_and_store_bottles_loop`、`_execute_split_liquid_async` 等）都会操作计数器
- 单例确保所有地方操作的是**同一个计数器对象**，避免数据不一致
- 所有计数变更都反映在同一个对象上，最终保存到同一个 `station_state.json` 文件

**使用示例：**
```python
# 在 cmd_handler.py 中任意位置
from station_counter import get_station_counter, StationCounter

station_counter = get_station_counter()
station_counter.increment(StationCounter.WAITING_SPLIT_AREA)  # +1
station_counter.decrement(StationCounter.SPLIT_DONE_250ML_AREA)  # -1
```

### 🔋 自动充电功能

新增模块 `battery_monitor.py`，实现机器人自动充电管理。

#### 功能概述

- 系统激活后自动启动电池监控
- 每10分钟检测所有已连接机器人的电池电量
- 电量低于30%时，等待当前任务完成后自动前往充电桩
- **电量达到99%时，自动返回对应机器人的home点位**
- 返回home点位后恢复正常工作

#### 配置参数

在 `constants.py` 中配置：

```python
# 自动充电功能开关
ENABLE_AUTO_CHARGING = True

# 电池电量检测间隔（秒）
BATTERY_CHECK_INTERVAL = 600  # 10分钟

# 低电量阈值（低于此值触发充电）
BATTERY_LOW_THRESHOLD = 0.30  # 30%

# 可接收任务阈值（充电时电量达到此值可接收新任务）
CHARGING_ACCEPT_TASK_THRESHOLD = 0.50  # 50%

# 充电完成阈值（高于此值返回home点位）
CHARGING_DONE_THRESHOLD = 0.99  # 99%

# 充电状态验证配置
CHARGING_STATUS_CHECK_DELAY = 60   # 导航到充电桩后等待检查充电状态的延迟时间（秒）
CHARGING_STATUS_MAX_RETRIES = 3    # 充电状态验证失败后最大重试导航次数

# 充电状态值
CHARGING_STATUS_NOT_CHARGING = 0   # 未充电
CHARGING_STATUS_CHARGING = 1       # 充电中
CHARGING_STATUS_COMPLETE = 2       # 充电完成

# 电池状态 topic
BATTERY_TOPIC = "/zj_humanoid/robot/battery_info"

# 充电桩导航点位
CHARGING_STATION_POSE = "charge"

# 充电完成后返回的home点位（按机器人类型分配）
CHARGING_DONE_HOME_POSES = {
    "robot_a": "home_transfer",  # Robot A -> 转运任务home点位
    "robot_b": "home_split",     # Robot B -> 分液任务home点位
}
CHARGING_DONE_HOME_POSE_DEFAULT = "home"  # 默认home点位
```

#### ⚠️ 重要说明：home点位配置

**home点位需要在两个地方配置：**

1. **导航点位常量** (`NavigationPose` 类) - 定义任务使用的导航点位
   ```python
   class NavigationPose:
       HOME_ROBOT_A = "home_transfer"  # 转运任务home点位
       HOME_ROBOT_B = "home_split"     # 分液任务home点位
   ```

2. **充电完成home点位** (`CHARGING_DONE_HOME_POSES`) - 定义充电完成后返回的点位
   ```python
   CHARGING_DONE_HOME_POSES = {
       "robot_a": "home_transfer",
       "robot_b": "home_split",
   }
   ```

**在本项目中，这两个配置的值是相同的**：
- Robot A 的充电完成home点位 = 任务home点位 = `home_transfer`
- Robot B 的充电完成home点位 = 任务home点位 = `home_split`

这样设计是为了保持灵活性，未来如果需要将充电完成返回点位与任务home点位分开，只需修改 `CHARGING_DONE_HOME_POSES` 即可。

#### 外部配置文件

在 `robot_config.json` 中配置：

```json

        "enabled": true,
        "require_battery_on_startup": true,

        "charging_accept_task_threshold": 0.50,
        "charging_done_threshold": 0.99,
        "charging_status_check_delay": 60,
        "charging_status_max_retries": 3,

            "robot_a": "home_transfer",

        }
```

#### 配置参数说明

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `low_threshold` | 0.30 | 低电量阈值，低于此值触发充电 |
| `charging_accept_task_threshold` | 0.50 | 可接收任务阈值，充电时电量达到此值可接收新任务 |
| `charging_done_threshold` | 0.99 | 充电完成阈值，高于此值自动返回home点位 |

#### 充电状态监控

系统通过订阅 `/zj_humanoid/chassis/charge_stats` topic 监控充电状态：

**充电状态参数：**
| 参数 | 类型 | 说明 |
|------|------|------|
| `battery_charging_status` | int | 0=未充电, 1=充电中, 2=充电完成 |
| `charge_port_connected` | bool | 充电口是否已连接 |

**充电状态验证流程：**

```
导航到充电桩成功
        ↓
等待 60 秒（可配置）
        ↓
检查充电状态
        ↓
battery_charging_status == 1？
    ├─是→ 确认充电中，继续监控电量
    └─否→ 充电异常
              ↓
        重试次数 <= 3？
            ├─是→ 重新导航到充电桩
            └─否→ 根据 charge_port_connected 判断错误原因
                    ├─ True  → 充电桩故障
                    └─ False → 导航定位问题
```

**错误诊断：**
| 条件 | 错误类型 | 说明 |
|------|----------|------|
| `charge_port_connected=True` 且 `battery_charging_status=0` | 充电桩故障 | 充电口已连接但未开始充电，可能是充电桩硬件问题 |
| `charge_port_connected=False` | 导航定位问题 | 充电口未连接，可能是导航到充电桩的位置不准确 |


3. 发布导航命令到 `/navigation_control` topic
4. 等待导航完成
5. 状态切换为 `normal`，恢复正常工作

### 🗄️ StorageManager 多机器人暂存区支持

#### 数据结构

```json
    "robot_a": {

    }

```

#### 自动迁移

- 系统自动检测旧格式数据并迁移到新格式
- 旧数据会被归入 `robot_a` 的存储空间

#### 主要方法签名变更

| 方法 | 旧签名 | 新签名 |
|------|-------|-------|

### 🔄 RESET_SYSTEM 系统重置功能

新增 `RESET_SYSTEM` 命令，用于在系统出现问题或需要重启时，将系统重置到初始休眠状态。

#### 功能说明

- **用途**：当系统处于异常状态或需要重新开始时，重置所有运行状态
- **效果**：系统回到刚启动时的休眠状态，等待 `START_WORKING` 命令激活
- **停止重连**：自动停止所有机器人的重连尝试，进入完全休眠
- **保留数据**：瓶子管理器中的瓶子数据会被保留，只重置运行时状态

#### 命令格式

```json
{
    "cmd_id": "RESET_SYSTEM_001",
    "cmd_type": "RESET_SYSTEM",
    "params": {}
}
```

**测试命令**：
```bash
curl -X POST http://localhost:8848 -d @test_commands/RESET_SYSTEM_command.json
```

#### 重置内容

执行 `RESET_SYSTEM` 后，以下内容会被重置：

| 重置项 | 说明 |
|-------|------|
| 机器人连接 | 停止所有机器人的重连尝试，关闭现有连接 |
| robots 字典 | 清空机器人实例，下次激活时重新创建 |
| start_working_event | 清除启动事件，需重新发送 START_WORKING |
| scan_enter_id_event | 清除扫码ID录入等待事件 |
| pick_from_opener_500_event | 清除500ml开瓶器等待事件 |
| pick_from_opener_250_event | 清除250ml开瓶器等待事件 |
| task_state_machine | 重置状态机到初始状态 |
| **配置文件** | **重新加载 robot_config.json（新增）** |
| **电池监控配置** | **使用新配置参数（新增）** |

#### 配置热更新功能

**RESET_SYSTEM 命令现在支持配置文件热更新**：

1. 修改 `robot_config.json` 配置文件
2. 发送 `RESET_SYSTEM` 命令
3. 新配置立即生效（无需重启 Docker 或程序）

**支持热更新的配置项**：
- 机器人连接配置（host、port）
- 自动充电参数（阈值、检测间隔等）
- WebSocket 服务器配置
- 其他所有 robot_config.json 中的配置

**使用场景**：
```bash
# 1. 修改配置文件（Docker外部挂载的配置文件）
vim /path/to/robot_config.json

# 2. 发送RESET_SYSTEM命令使配置生效
curl -X POST http://localhost:8090 -d @test_commands/RESET_SYSTEM_command.json

# 3. 发送START_WORKING激活系统（使用新配置）
curl -X POST http://localhost:8090 -d @test_commands/START_WORKING_command.json
```

#### 关键特性：完全休眠模式

在休眠状态下，系统**只有HTTP服务器在运行**，不会有任何机器人连接或重连尝试。

##### 实现机制

**1. main.py 主循环架构**

```
┌─────────────────────────────────────────┐
│            外层循环 (while True)         │
│  ┌─────────────────────────────────┐    │
│  │  进入休眠状态                     │    │
│  │  (只有HTTP服务器运行)             │    │
│  └──────────────┬──────────────────┘    │
│                 ↓                        │
│  ┌─────────────────────────────────┐    │
│  │  等待 START_WORKING              │    │
│  └──────────────┬──────────────────┘    │
│                 ↓                        │
│  ┌─────────────────────────────────┐    │
│  │  创建并连接机器人                 │    │
│  │  (检查 reset_system_event)       │    │
│  └──────────────┬──────────────────┘    │
│                 ↓                        │
│  ┌─────────────────────────────────┐    │
│  │  工作循环                        │    │
│  │  (每秒检查 reset_system_event)   │←──┐│
│  └──────────────┬──────────────────┘   ││
│                 ↓                       ││
│  ┌─────────────────────────────────┐   ││
│  │  收到 RESET_SYSTEM?              │   ││
│  │  是 → 清理 → 回到休眠            │───┘│
│  │  否 → 继续工作                   │────┘
│  └─────────────────────────────────┘    │
└─────────────────────────────────────────┘
```

**2. RobotController 停止重连机制**

```python
# RobotController 新增属性和方法
self._stop_reconnect = False  # 停止重连标志

def stop_reconnect(self):
    """停止重连尝试"""
    self._stop_reconnect = True

def reset_reconnect(self):
    """重置重连标志，允许重新连接"""
    self._stop_reconnect = False
```

**3. cmd_handler 重置事件**

```python
# CmdHandler 新增事件
self.reset_system_event = threading.Event()

# handle_reset_system 中触发
self.reset_system_event.set()
```

**4. 连接过程中断检查**

- 机器人连接在单独线程中执行
- 主线程每0.5秒检查一次 `reset_system_event`
- 收到重置命令时立即调用 `robot.stop_reconnect()` 中断连接

#### 使用场景

1. **异常恢复**：任务执行过程中出现错误，需要重新开始
2. **手动重启**：操作人员需要手动停止当前任务并重新开始
3. **调试测试**：开发调试时快速重置系统状态

#### 使用流程

```
正常运行中 / 异常状态
       |
       v
  RESET_SYSTEM (重置)
       |
       v
   休眠状态
       |
       v
  START_WORKING (激活)
       |
       v
   正常工作
```

#### 响应示例

**成功响应**：
```json

  "success": true,
  "message": "系统已重置到休眠状态，发送START_WORKING命令可重新激活",

}
```

**失败响应**：

## 🔄 SCAN_QRCODE 异步状态机功能

### 功能概述

- 后台线程执行扫码任务
- HTTP端可通过**GET_TASK_STATE**接口主动查询任务状态

#### 1. 立即响应

```bash
  "message": "SCAN_QRCODE任务已启动",
  "cmd_id": "cmd_scan_qrcode_001",
  "note": "使用 GET_TASK_STATE 命令查询任务状态"
}
```

#### 2. 状态机管理

完整的扫码流程步骤：

| 步骤 | 状态名称 | 说明 |
|-----|---------|------|
| 1 | NAVIGATING_TO_SCAN | 导航到扫描台 |
| 2 | GRAB_SCAN_GUN | 抓取扫描枪（可选） |
| 3 | CV_DETECTING | 视觉检测瓶子 |
| 4 | GRABBING_BOTTLE | 抓取瓶子 |
| 5 | PUT_TO_SCAN_MACHINE | 放置到扫描转盘 |
| 6 | WAITING_ID_INPUT | 等待ID录入 |
| 7 | ID_INPUT_SUCCESS | ID录入成功 |
| 8 | PUTTING_TO_BACK | 放置到后部暂存区 |
| 9 | TURNING_BACK_FRONT | 转回正面 |
| 10 | NAVIGATING_TO_SPLIT | 导航到分液台 |
| 11 | PUTTING_DOWN | 放下瓶子到分液台 |

**步骤6说明**：步骤5执行成功后，系统等待HTTP发送 `SCAN_QRCODE_ENTER_ID` 命令录入瓶子ID信息。

**步骤11说明（双手抓放优化）**：

放下瓶子到分液台时，采用双手协同操作提高效率：

```
瓶子处理流程（每次最多2个）：

1. 转腰到后部暂存区
         |
         v
2. 右手抓起瓶子1
         |
         v
3. 左手抓起瓶子2（如有）
         |
         v
4. 转腰到正面
         |
         v
5. 右手放下瓶子1
         |
         v
6. 左手放下瓶子2（如有）
         |
         v
   下一对瓶子...
```

| 场景 | 操作方式 |
|-----|---------|
| 偶数个瓶子 | 双手同时操作，每轮处理2个 |
| 奇数个瓶子 | 最后一个只用右手 |
| 1个瓶子 | 仅右手操作 |

**优势**：
- 减少转腰次数（每2个瓶子只需转腰2次，而非4次）
- 提高整体效率约40%

## 📡 ROS Topic订阅功能

### 功能概述

为支持实时获取机器人状态（如导航状态），在`robot_controller.py`中新增了ROS topic订阅功能。基于rosbridge协议，支持订阅任意ROS topic并获取最新消息。

### 核心API

#### 1. 订阅Topic

```python
# 订阅导航状态topic
robot.subscribe_topic(
    topic_name="/navigation_status",      # topic名称
    msg_type="NavigationStatus",          # 消息类型
    throttle_rate=0,                      # 节流速率(ms)，0=不节流
    queue_length=1                        # 队列长度
)
```

#### 2. 获取最新消息

```python
# 获取topic的最新消息
nav_status = robot.get_topic_message("/navigation_status")

if nav_status:
    print(f"导航状态: {nav_status}")
    # nav_status是字典格式，包含消息的所有字段
else:
    print("尚未收到消息")
```

#### 3. 取消订阅

```python
# 取消订阅topic
robot.unsubscribe_topic("/navigation_status")
```

### 🔧 WebSocket并发冲突修复（ConcurrencyError）

#### 问题描述

**错误信息**：
```
websockets.exceptions.ConcurrencyError: cannot call recv while another coroutine is already running recv or recv_streaming
```

**问题根因**：
在同时支持 ROS Topic 订阅和服务请求时，出现了 WebSocket 并发冲突：
- `_topic_message_listener` 协程持续调用 `websocket.recv()` 监听 topic 消息
- `send_service_request` 的 `_async_send_and_receive` 也调用 `websocket.recv()` 等待服务响应
- WebSocket 库不允许多个协程同时调用 `recv()` 方法

#### 解决方案：统一消息监听器

采用**单一接收者模式**，所有 WebSocket 消息统一接收后再分发：

```python
# robot_controller.py

# 1. 添加 Future 支持
def __init__(self, ...):
    self.service_response_future = None  # 用于服务响应传递
    self._topic_listener_started = False

# 2. 统一消息监听器（唯一的 recv() 调用者）
async def _unified_message_listener(self):
    """统一接收所有 WebSocket 消息"""
    while self.connected and self.websocket:
        try:
            message_str = await asyncio.wait_for(self.websocket.recv(), timeout=1.0)
            message = json.loads(message_str)
            
            op = message.get("op")
            
            if op == "publish":
                # Topic 消息 → 存储到缓存
                topic_name = message.get("topic")
                msg_data = message.get("msg")
                if topic_name in self.subscribed_topics:
                    self.topic_messages[topic_name] = msg_data
            else:
                # 服务响应 → 通过 Future 传递
                if self.service_response_future and not self.service_response_future.done():
                    self.service_response_future.set_result(message_str)

# 3. 服务请求通过 Future 等待响应
async def _async_send_and_receive(self, request_str, maxtime=120):
    self.service_response_future = asyncio.Future()
    await self.websocket.send(request_str)
    # 等待统一监听器传递响应（不直接调用 recv）
    response_str = await asyncio.wait_for(self.service_response_future, timeout=maxtime)
    return response_str
```

#### 架构对比

**修改前（多接收者 - 有冲突）**：
```
┌──────────────────┐         ┌────────────────┐
│ Topic Listener   │         │ Service Request│
│  websocket.recv()│         │ websocket.recv()│ ← ConcurrencyError!
└──────────────────┘         └────────────────┘
```

**修改后（单接收者 - 无冲突）**：
```
        ┌─────────────────────────────┐
        │  Unified Message Listener   │
        │    websocket.recv() ←唯一   │
        └──────────┬──────────────────┘
                   │
         ┌─────────┴─────────┐
         ↓                   ↓
  ┌──────────────┐    ┌──────────────┐
  │ Topic 消息    │    │ 服务响应      │
  │ → 存储缓存    │    │ → Future传递  │
  └──────────────┘    └──────────────┘
```

#### 关键代码位置

| 文件 | 行数 | 说明 |
|-----|------|------|
| `robot_controller.py` | 27 | 添加 `service_response_future` |
| `robot_controller.py` | 86-91 | 重连时重置监听器标志和清空缓存 |
| `robot_controller.py` | 332-342 | 修改 `_async_send_and_receive` 使用 Future |
| `robot_controller.py` | 517-563 | 新增 `_unified_message_listener` |
| `robot_controller.py` | 455-463 | 启动统一消息监听器 |

#### 技术要点

1. **单一接收者**：只有 `_unified_message_listener` 调用 `websocket.recv()`
2. **消息分发**：根据 `op` 字段判断消息类型并分发
3. **Future 传递**：服务响应通过 `asyncio.Future` 传递给等待协程
4. **生命周期管理**：重连时重置 `_topic_listener_started` 标志

#### 优势

- ✅ 彻底解决 WebSocket 并发冲突
- ✅ 支持同时进行 Topic 订阅和服务请求
- ✅ 代码结构更清晰，消息处理统一管理
- ✅ 异常处理更容易（统一入口）

### 连接断开容错处理

#### 问题场景

在SCAN_QRCODE流程中，导航到扫描台的最后阶段可能会出现网络断开。传统方式下，连接断开会导致整个任务失败。

#### 解决方案

实现了 `_wait_for_topic_message()` 方法，支持连接断开自动等待重连：

```python
def _wait_for_topic_message(self, topic_name: str, timeout: float = 10.0, 
                            retry_on_disconnect: bool = True) -> Optional[Dict]:
    """
    等待并获取topic消息（支持连接断开重连）
    
    参数:
        topic_name: topic名称
        timeout: 超时时间（秒）
        retry_on_disconnect: 连接断开时是否等待重连
    
    返回:
        dict: topic消息，如果超时返回None
    """
    # 循环检查连接状态和消息
    while 未超时:
        if 连接断开:
            if retry_on_disconnect:
                # 等待重连（最多30秒）
                等待连接恢复()
                # 重新订阅topic
                重新订阅()
            else:
                return None
        
        # 尝试获取消息
        msg = robot.get_topic_message(topic_name)
        if msg:
            return msg
        
        time.sleep(0.5)  # 等待后重试
```

#### 工作流程

```
执行流程:
┌─────────────────────┐
│ 等待topic消息       │
└──────────┬──────────┘
           │
           ▼
    ┌──────────────┐
    │ 检查连接状态  │
    └──────┬───────┘
           │
    ┌──────┴───────┐
    │              │
已连接           已断开
    │              │
    ▼              ▼
获取消息      ┌──────────────┐
    │        │ 等待重连(30秒) │
    │        └──────┬─────────┘
    │               │
    │        ┌──────┴────────┐
    │        │               │
    │    重连成功        重连失败
    │        │               │
    │        ▼               ▼
    │   重新订阅topic    返回None
    │        │
    │        └───────┐
    │                │
    └────────────────┤
                     ▼
                 返回消息
```

#### 使用示例

```python

    topic_name="/navigation_status",
    timeout=10,                    # 最多等待10秒
    retry_on_disconnect=True       # 支持断开重连
)

if nav_status:
    print(f"✓ 导航状态: {nav_status}")
else:
    print("⚠️  未收到导航状态消息")
```

| 特性 | 说明 |
|-----|------|
| **自动检测断开** | 每0.5秒检查一次连接状态 |
| **等待重连** | 连接断开后等待最多30秒重连 |
| **自动重订阅** | 重连成功后自动重新订阅topic |
| **超时控制** | 支持设置总超时时间 |
| **可配置** | 可选择是否支持断开重连 |

## 🔌 WebSocket客户端模式

### 功能概述

系统现支持作为 WebSocket **客户端**主动连接外部 WebSocket 服务器，与现有的 WebSocket 服务器模式（接受外部连接）形成互补。

**两种模式对比：**

| 模式 | 方向 | 用途 |
|------|------|------|
| **WebSocket服务器** | 外部设备 → 本系统 | 接受上层调度系统的命令 |
| **WebSocket客户端** | 本系统 → 外部服务器 | 主动连接上层系统推送数据 |

### 配置说明

在 `robot_config.json` 中配置：

```json
{
    "websocket_client": {
        "enabled": false,
        "server_host": "192.168.1.100",
        "server_port": 8091,
        "ssl_enabled": false,
        "client_id": "robot_connect_client",
        "reconnect_interval": 5,
        "reconnect_max_attempts": null,
        "heartbeat_interval": 30
    }
}
```

**配置参数说明：**

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `enabled` | bool | false | 是否启用客户端 |
| `server_host` | string | "127.0.0.1" | 目标服务器地址 |
| `server_port` | int | 8091 | 目标服务器端口 |
| `ssl_enabled` | bool | false | 是否使用 wss:// 加密连接 |
| `client_id` | string | "robot_connect_client" | 客户端标识 |
| `reconnect_interval` | int | 5 | 断开后重连间隔（秒） |
| `reconnect_max_attempts` | int/null | null | 最大重连次数，null=无限 |
| `heartbeat_interval` | int | 30 | 心跳间隔（秒） |

### Client ID 通信方式

客户端模式使用**主动注册**方式进行身份标识（与服务器模式相反）：

| 模式 | Client ID 来源 | 流程 |
|------|---------------|------|
| **服务器模式** | 服务端分配 | 客户端连接 → 服务端分配ID → 客户端使用 |
| **客户端模式** | 客户端主动发送 | 连接服务器 → 主动发送ID注册 → 服务端记录 |

**通信流程：**

```
┌─────────────┐                    ┌─────────────┐
│  本系统      │                    │  外部服务器   │
│ (WebSocket  │                    │ (WebSocket  │
│   Client)   │                    │   Server)   │
└──────┬──────┘                    └──────┬──────┘
       │                                  │
       │  1. 建立WebSocket连接             │
       │─────────────────────────────────>│
       │                                  │
       │  2. 发送注册消息                  │
       │  {"type":"register",             │
       │   "client_id":"robot_xxx",       │
       │   "timestamp":"..."}             │
       │─────────────────────────────────>│
       │                                  │
       │  3. (可选) 服务端确认             │
       │  {"type":"register_ack",...}     │
       │<─────────────────────────────────│
       │                                  │
       │  4. 后续通信使用此client_id        │
       │<────────────────────────────────>│
```

**注册消息格式（客户端发送）：**
```json
{
    "type": "register",
    "client_id": "robot_connect_client",
    "timestamp": "2026-01-27T10:30:00.000000"
}
```

**服务端确认（可选）：**
```json
{
    "type": "register_ack",
    "client_id": "robot_connect_client",
    "message": "注册成功"
}
```

**后续消息格式（自动携带client_id）：**
```json
{
    "cmd_type": "GET_TASK_STATE",
    "cmd_id": "task_001",
    "params": {},
    "client_id": "robot_connect_client"
}
```

### 使用方法

#### 1. 设置消息处理回调

```python
from websocket_client import get_websocket_client

client = get_websocket_client()
if client:
    def handle_message(data):
        print(f"收到服务端消息: {data}")
        # 处理逻辑...
    
    client.set_message_callback(handle_message)
```

#### 2. 发送消息到服务器

```python
# 方式一：发送原始消息
client.send({
    "type": "status_report",
    "data": {"robot_a": "idle", "robot_b": "working"}
})

# 方式二：发送命令（自动生成cmd_id）
client.send_command("REPORT_STATUS", params={"status": "ready"})

# 方式三：发送命令并等待响应
response = client.send_and_wait(
    cmd_type="QUERY_TASK",
    params={"task_id": "task_001"},
    timeout=10
)
if response:
    print(f"收到响应: {response}")
```

#### 3. 检查连接状态

```python
if client.is_connected:
    print(f"已连接，Client ID: {client.client_id}")
```

### 自动重连机制

- 连接断开后自动尝试重连
- 可配置重连间隔和最大重连次数
- 重连成功后自动重置计数器

### 与 RESET_SYSTEM 的集成

发送 `RESET_SYSTEM` 命令时，WebSocket 客户端配置会自动重新加载，无需重启程序即可更新配置。
