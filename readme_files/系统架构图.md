### 1.3 机器人控制层：Action 客户端三层分层

> 背景：ROS Action（actionlib topic 协议）是系统调用机器人长时任务（导航、
> 操作/task）的主要手段。为了让"传输机制"和"某个 Action 的业务语义"不再耦合，

**分层规则**：

| 新增需求 | 该在哪一层落地 |
|---|---|
| 新增一个同契约（`task/area/extra_params` → `success/error_msg/return_params`）的 Action | **仅** `task_utils`：换一个 `ActionSpec` 传入 `send_task_action(..., spec=...)` 即可 |
| 新增一个全新契约（Goal/Feedback/Result 字段完全不同）的 Action | 新增 `hardware/<domain>_utils.py`：自持自己的 `ActionSpec` + 领域数据结构 + `succeeded_check`，调用 `action_utils.send_action` |
| 修改 goal_id 生成规则、断线重连策略、cancel 超时等 | **仅** `action_utils` |
| 新增 ROS 话题/服务名 | `infrastructure/constants.py` |

**示例：一次 `send_task_action` 的完整调用栈**

```
cmd_handler._scan_and_store_bottles_loop_press_button()
  │
  │ send_task_action(robot, task="SCAN_TABLE", feedback_callback=on_fb)
  ▼
task_utils.send_task_action                  ← 领域层：构造 Goal，
  │ goal = {robot_task_types:{value:0},      包装 feedback 回调，
  │         task:"SCAN_TABLE",               成功判定用 _task_success_check
  │         area:"", extra_params:""}
  │
  │ send_action(robot, CHEM_PROJECT_ACTION_SPEC,
  │             goal, succeeded_check=_task_success_check, ...)
  ▼
action_utils.send_action                     ← 传输层：goal_id 生成，
  │ subscribe /chem_project/feedback         订阅、发布、轮询、断线重连
  │ subscribe /chem_project/result
  │ publish  /chem_project/goal   (ChemProjectActionGoal)
  │ while not terminal:
  │     poll topic_messages → call feedback_callback
  │ parse result → ActionResult
  ▼
robot_controller                             ← 连接层：WebSocket 收发
  │ ws.send({"op":"subscribe", ...})
  │ ws.send({"op":"publish",  ...})
  ▼
rosbridge  ──►  /chem_project 节点           ← 机器人 ROS 系统
```

返回值则沿反方向逐层"加壳"：

```
ChemProjectActionResult (ROS 消息)
    → ActionResult   (action_utils，含 goal_id / status_code / inner / succeeded)
    → TaskResult     (task_utils，含 succeeded / error_msg / return_params / __bool__)
    → 业务代码: `if not res: set_error(res.error_msg)`
                 `payload = res.parse_return_params() or {}`
```

## 4. 步骤拆分的必要性分析

以 `put_to_bottle_opener` 动作为例，说明为什么需要细粒度的步骤拆分：

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                        SPLIT_LIQUID 分液任务流程                                 │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  ┌─────────────────────────────────────────────────────────────────────────┐   │
│  │ 步骤7: 抽水 (pouring_water)                                             │   │
│  │                                                                          │   │
│  │   robot.send_service_request("pouring_water", volumn=200)               │   │
│  │                         │                                                │   │
│  │   【必须拆分原因】                                                        │   │
│  │   • 抽水量(volumn)来自上层任务参数                                        │   │
│  │   • 抽水完成后才能进行下一步                                              │   │
│  │   • 需要更新 TaskStateMachine 状态供外部查询                             │   │
│  └─────────────────────────┬───────────────────────────────────────────────┘   │
│                            ▼                                                    │
│  ┌─────────────────────────────────────────────────────────────────────────┐   │

│  │                                                                          │   │

│  │                         │                                                │   │
│  │   【必须拆分原因】                                                        │   │
│  │   • target_pose 参数区分500ml/250ml开瓶器                                │   │
│  │   • 放置完成后，机器人需要让出位置给开瓶器工作                            │   │

│  ║                                                                          ║   │
│  ║  【关键交互点】                                                           ║   │
│  ║  • 开瓶器(PLC设备)工作中，机器人在旁等待                                 ║   │
│  ║  • 开瓶器完成后，工厂调度系统发送HTTP命令:                               ║   │
│  ║    PICK_FROM_BOTTLE_OPENER_500_command.json                              ║   │
│  ║  • 系统收到命令后，触发 pick_from_opener_500_event                       ║   │
│  ║  • 这是 "人机协作" 的关键同步点                                          ║   │

│  │                                                                          │   │
│  │   robot.send_service_request("pick_from_bottle_opener",                 │   │
│  │       target_pose="bottle_opener_500")                                   │   │
│  └─────────────────────────────────────────────────────────────────────────┘   │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 4.1 步骤拆分的六大必要性

| 原因 | 说明 | 示例 |
|------|------|------|
| **1. 参数传递** | 每个动作需要特定参数，来自上层任务或运行时计算 | `target_pose="bottle_opener_500"` 区分设备 |
| **2. 外部系统同步** | 需要等待PLC设备/开瓶器等完成工作 | `pick_from_opener_500_event.wait()` |
| **3. 状态追踪** | 每步需更新状态机，供外部查询进度 | `task_state_machine.update_step()` |
| **4. 错误处理** | 每步独立判断成功/失败，便于定位和恢复 | `if not result: set_error()` |
| **5. 并行执行** | 某些步骤可并行（如双手操作） | 步骤9和步骤10并行执行 |
| **6. 可中断性** | 支持在任意步骤暂停/取消任务 | `reset_system_event` 检查 |

## 8. 总结

本系统采用**分层架构**设计：

1. **通信接入层**：统一接收外部命令（HTTP/WebSocket/Modbus）
2. **命令调度层**：解析命令、编排任务流程、协调多步骤执行
3. **业务逻辑层**：状态管理、资源管理、安全控制
4. **机器人控制层**：与实际机器人通信、执行动作
   - 4a. **Action 传输层**（`hardware/action_utils.py`）：通用 actionlib topic 客户端
   - 4b. **Action 领域层**（`hardware/navigation_utils.py` / `hardware/task_utils.py`）：各自封装领域 Spec + 数据结构 + 成功判定
   - 4c. **连接层**（`hardware/robot_controller.py`）：WebSocket / ROS Bridge 协议

**Action 三层分层的核心价值**（详见 1.3 节）：
- **传输层不知道"这是什么 Action"**：新增 Action 类型不用改 `action_utils`
- **领域层只关注业务字段**：调用方拿到的是 `NavigationResult.succeeded` / `TaskResult.parse_return_params()`，不再处理原始 inner dict
- **新增同契约 Action**：换一个 `ActionSpec` 即可，不再是改大段代码
- **同构的导航与操作**：`send_navigation_action` / `send_task_action` 行为一致（feedback 回调、超时取消、断线重连、`if not result:` 判定）

**步骤拆分的核心价值**：
- 支持与外部系统（PLC、MES）的同步交互
- 提供细粒度的状态追踪和错误处理
- 实现参数的动态计算和传递
- 保证系统的可中断性和可恢复性
