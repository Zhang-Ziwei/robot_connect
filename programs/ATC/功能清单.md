# ATC 项目功能清单

> 零件转移任务处理器，两台机器人并行执行，与旧项目完全解耦。

---

## 项目结构

```
programs/ATC/
├── ATC.py               # 任务处理器主文件（ATCHandler）
├── plc_modbus.py        # ATC 传送带 Modbus TCP 客户端（ConveyorController）
├── constants.py         # ATC 专属常量（点位 / 步骤 / 服务名 / PLC / 超时）
├── robot_config.json    # ATC 项目内置导航点位配置（navigation_poses.ATC）
├── 功能清单.md           # 本文件
├── atc_p2_slots.json    # P2 槽位状态持久化（运行时自动生成）
├── atc_p3_slots.json    # P3 槽位状态持久化（运行时自动生成）
└── atc_p4_slots.json    # P4 槽位状态持久化（运行时自动生成）
```

> `plc_modbus.py` 是 Modbus TCP **客户端**，连接真实传送带 PLC；  
> 与 `plc_controller/plc_modbus.py`（Modbus TCP **服务器**，模拟 PLC 端）角色相反，两者不互相依赖，底层均使用 `pymodbus`。

## 接收的 HTTP 命令

### 任务启动命令

| cmd_type | 说明 |
|---|---|
| `TRANS_COMPONENT` | 单次启动零件转移任务（异步，P2 预置为 FULL，立即开始分拣） |
| `ATC_NEXT_STEP`   | 人工确认后触发任务继续执行 |

### 流程控制命令（配合传送带使用）

| cmd_type | 说明 | 返回 |
|---|---|---|
| `PROCESS_BEGINS`          | 全流程启动（连续模式）。两台机器人持续循环，P2 初始为 EMPTY，等待第一次 MANUAL_RESET_COMPLETED | `"已接收PROCESS_BEGINS命令，流程开始工作"` |
| `PROCESS_PAUSED`          | 暂停流程，当前最小颗粒度动作（service call）完成后生效 | 成功消息 |
| `PROCESS_RESUMED`         | 恢复暂停的流程 | 成功消息 |
| `PROCESS_ENDED`           | 结束流程，后续步骤不再执行，取消任务状态 | 成功消息 |
| `MANUAL_RESET_COMPLETED`  | 人工复位完成：P4 标记为 EMPTY（人工取走满箱）+ 后台启动传送带正转 → 完成后 P2 置 FULL | 成功消息 |

> **最小调度颗粒度**：每次 `robot.send_service_request_task(...)` 返回后。暂停在此之后生效，不会打断机械臂动作中途。

## 任务流程

### robot_a — 分拣搬运流程

```
[等待] P2 有物料（初次由 MANUAL_RESET_COMPLETED 触发传送带送料）
① P2 取零件B
② P3（空箱子槽位）放零件B  → 槽位状态 EMPTY → HALF
③ P2 取螺丝
④ P3（同槽位）放螺丝
⑤ P1 取零件A
⑥ P3（同槽位）放零件A      → 槽位状态 HALF → FULL  ← 分拣完成，触发传送带反转
⑦ 导航到 P4，等待 P4 变为 EMPTY（robot_b 装配完成 / 人工取走）
⑧ 把 P4 空箱子搬到 P3 空槽  → P4→NO_BOX, P3_空槽→EMPTY
⑨ 把 P3 满箱子搬到 P4      → P3_满槽→NO_BOX, P4→FULL
[连续模式] 回到第①步，等待下一次 MANUAL_RESET_COMPLETED
[单次模式] 流程结束
```

### robot_b — 装配流程

```
[等待] P4 有满箱子（robot_a 搬来后触发）
① 执行装配（ASSEMBLY 服务调用）
[连续模式] 回到等待步骤
[单次模式] 流程结束
```

两条流程并行启动，全部完成后整体任务变为 COMPLETED；任意一条报错则整体变为 ERROR；收到 PROCESS_ENDED 则变为 CANCELLED。

### 连续循环时序

```
PROCESS_BEGINS
    ↓
[robot_a] 等待 P2 FULL ←─────────────────────────────────────────┐
    ↓                                                              │
MANUAL_RESET_COMPLETED: P4→EMPTY, 传送带正转 → P2→FULL            │
    ↓                                                              │
[robot_a] 分拣（T1-T3）→ P2→EMPTY → 传送带反转                    │
    ↓                                                              │
[robot_a] 搬箱子（T4）→ P4→FULL                                   │
    ↓                                                              │
[robot_b] 装配 → 装配完成                                          │
    ↓                                                              │
MANUAL_RESET_COMPLETED（人工取走满箱，传送带送新料） ───────────────┘
    ↓
PROCESS_ENDED（结束流程）
```

## 槽位状态机（P3 / P4）

| 状态 | 含义 |
|---|---|
| `EMPTY`  | 槽位有空箱子，可放零件 |
| `HALF`   | 箱子已放了部分零件，可继续放 |
| `FULL`   | 箱子已满，等待搬走 |
| `NO_BOX` | 槽位无箱子 |

状态持久化到 JSON 文件，重启不丢失。

## 导航点位配置说明

`NavigationPose` 中的坐标在模块加载时从 `robot_config.json` 动态覆盖，硬编码值保留作兜底。

**加载优先级（高→低）：**
```
1. /config/robot_config.json        ← Docker 外部挂载（现场调试用）
2. programs/ATC/robot_config.json   ← 本项目内置配置
3. infrastructure/robot_config.json ← 全局兜底配置
```

**修改点位坐标：** 在对应 `robot_config.json` 的 `navigation_poses.ATC` 节下修改，重启后生效。

```json
{
    "navigation_poses": {
        "ATC": {
            "P1":     [[-0.96, -0.92, 0.0, 0.0, 0.0, 1.00, -0.05]],
            "P1_mid": [[0.07, 0.89, 0.0, 0.0, 0.0, -0.68, 0.73],
                       [-0.96, -0.92, 0.0, 0.0, 0.0, 1.00, -0.05]]
        }
    }
}
```

**防呆机制：** 若 config 中 key 拼写错误或坐标格式非法，系统打印警告并自动回退到硬编码默认值，不会崩溃。

### 传送带 PLC 配置说明（`plc_modbus.py`）

传送带控制使用 Modbus TCP（客户端模式，连接真实 PLC 设备），实现在 `programs/ATC/plc_modbus.py` 的 `ConveyorController` 中。

**寄存器协议（由 `ATCConveyorRegisters` 定义）：**

| 寄存器 | 地址 | 操作 | 值 | 含义 |
|---|---|---|---|---|
| 控制寄存器 | 0 | 写 | 0 | 停止（运动结束后必须写停止，PLC 才归空闲）|
| 控制寄存器 | 0 | 写 | 1 | 正转 |
| 控制寄存器 | 0 | 写 | 2 | 反转 |
| 状态寄存器 | 3 | 只读 | 0 | 空闲就绪（初始状态）|
| 状态寄存器 | 3 | 只读 | 1 | 运行中 |
| 状态寄存器 | 3 | 只读 | 2 | 运行完成（需写停止才能归空闲）|

**职责分层原则：**

| 层 | 代码位置 | 职责 |
|---|---|---|
| PLC 操作层 | `plc_modbus.ConveyorController` | 只负责 Modbus TCP 通信（写寄存器 / 轮询状态 / 写停止），不含任何业务语义 |
| PLC 调用层 | `ATC._run_conveyor_forward()` | 封装"正转→等完成"的 PLC 调用序列，返回 bool，不修改槽位状态 |
| 业务逻辑层 | `ATC.handle_manual_reset_completed` 的后台线程 | 无论 PLC 是否成功，都将 P1 设为 FULL；PLC 失败时降级为 WARNING，不阻塞主流程 |

示例（`MANUAL_RESET_COMPLETED` 后台线程的实际调用链）：
```
_on_manual_reset()
  └── _run_conveyor_forward()  → 纯 PLC 操作，返回 True/False
        └── ConveyorController.forward() + wait_done()
  └── 无论 conveyor_done 是 True 还是 False：
        p1_tracker.set_state("P1", FULL)  ← 业务逻辑与 PLC 解耦
        （PLC 失败时打印 WARNING，流程继续，不会卡死在等待 P1 物料循环中）
```

> **降级模式说明：** 若 pymodbus 未安装或 PLC 连接失败，传送带指令会立即返回失败。此时系统不会阻塞——P1 直接被标记为 FULL，robot_a 可继续分拣流程，与 `ConveyorController` 文档中声明的设计意图一致。

**`ATCHandler` 初始化规则：**

- `ATCHandler(robots=...)` — 不传 `conveyor`，内部自动创建 `ConveyorController()`（正常使用）
- `ATCHandler(robots=..., conveyor=None)` — 显式传 `None`，跳过真实 PLC（测试 / mock 模式）
- `ATCHandler(robots=..., conveyor=my_conveyor)` — 注入自定义实例（覆盖配置或 mock）

PLC IP 在 `ATCConveyorConfig.HOST` 中配置。

```python
# HTTP 路由映射（在 cmd_handler.py 中已配置）
"PROCESS_BEGINS"         → atc.handle_process_begins(cmd_data)
"PROCESS_PAUSED"         → atc.handle_process_paused(cmd_data)
"PROCESS_RESUMED"        → atc.handle_process_resumed(cmd_data)
"PROCESS_ENDED"          → atc.handle_process_ended(cmd_data)
"MANUAL_RESET_COMPLETED" → atc.handle_manual_reset_completed(cmd_data)
"TRANS_COMPONENT"        → atc.handle_trans_component(cmd_data)   # 单次模式
"ATC_NEXT_STEP"          → atc.handle_next_step(cmd_data)
```

## 变更记录

### 2026-06-12 — 导航后流程卡死修复 + `is_robot_at_pose` 增强

**Bug 修复：ATC 导航完成后流程卡死**

- **现象：** `MANUAL_RESET_COMPLETED` 发出后，robot_a 线程完成到 P1_mid 的导航，但随后不执行任何后续操作，日志无报错，等待约 30 分钟后才超时退出。
- **根因：** 传送带 PLC 不可连接时（测试环境），`_on_manual_reset` 后台线程调用 `_run_conveyor_forward()` 立即返回 `False`，P1 状态始终为 `EMPTY`，导致 robot_a 卡在"等待 P1 物料就绪"循环（`P1_WAIT = 1800s`）。
- **修复（`ATC.py`）：** 无论传送带是否成功，都执行 `p1_tracker.set_state("P1", FULL)`；PLC 失败时降级为 `WARNING` 日志，主流程不中断。

**功能增强：`is_robot_at_pose` 支持多段路径**

- **背景：** `NavigationPose` 属性（如 `NavigationPose.P1`）加载后格式为 `list-of-tuples`，旧版 `is_robot_at_pose` 只接受单元组，调用时触发 `TypeError`（被 except 吞掉），导致每次判断都额外等待 5 秒 odom 超时。
- **修复（`hardware/navigation_utils.py`）：** `is_robot_at_pose` 入参增加对 `list-of-tuples` 的自动处理，取最后一个路点（目标终点）进行比较；单元组调用方式不变，向后兼容。
- **ATC.py 变更：** 移除临时辅助方法 `_at_pose`，直接使用增强后的 `is_robot_at_pose`。
